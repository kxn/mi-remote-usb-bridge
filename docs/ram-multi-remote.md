# 多遥控器前的 RAM 评估

日期：2026-09-16。基线是当前联通适配开发版 `0.6.6-unicom-dev`，RV32 ILP32、release 配置；尚未刷板验证。本轮统一按键代码位于上位机，不增加 MCU RAM。

## 当前测量

`build/fw-unicom/ch582f.elf` / `.map`：静态 RAM 结束地址 `0x20006598`，保留栈起点 `0x20007000`，两者间余量 **2664 字节**。构建要求至少保留 2048 字节，超出这个最低线仅 **616 字节**。不能把 2664 全部视为可用的第二连接预算。

| 对象 | 字节 | 说明 |
|---|---:|---|
| 产品状态 singleton | 5656 | 含队列、音频池和设备/协议状态 |
| BLE `MEM_BUF` | 6144 | 协议栈堆；静态尺寸不代表运行峰值 |
| 适配器 `g_adapter` | 1912 | 当前为单实例 |
| USB TX ring | 512 | 与流量和发送延迟有关 |
| EP2 buffer | 128 | USB 端点缓冲 |

以上不是完整 RAM 求和表。高代码区约 9144 字节也占 RAM，预留栈为 4096 字节。

用目标编译器对 `sizeof` 编译成数组，再用 `nm -S` 读取，适配器细分为：

| 字段 | 字节 |
|---|---:|
| 原始 HID Report Map | 512 |
| 解析后的 Report Map | 964 |
| 其中 fields[64]（包含在上一行） | 896 |
| Report 特征列表 | 96 |
| 各 Report 当前键状态 | 64 |
| 联通运行状态 | 88 |
| ATVV 运行状态类型 | 92 |

原始 Map 和解析 Map 合计 **1476 字节，占适配器约 77%**。各项可能有结构体对齐，不能将表中所有行直接相加。

## 优先优化方向

1. **分开发现阶段和运行阶段。** 原始 Map 主要用于发现、校验和解析；发现工作串行化后，有机会让多个连接共享 512 字节工作区。注意解析器会初始化输出，不能未经改造就把原始输入和解析输出直接放进同一个 union。
2. **把通用解析结果压缩成运行计划。** 当前已知两种方案，并不意味着每个连接都要永久保留最多 64 个通用字段。可保留发现时的完整验证，随后只保存实际通知解码所需信息。潜在收益大于直接削减 USB 队列；具体节省需实现后重新测量。
3. **互斥方案状态使用 union。** 单个连接只跑一个方案，可研究 ATVV 与联通运行状态共用空间；收益仅几十字节，不是主要来源。
4. **保留单路语音优先。** 两个遥控器同时收按键、最多一个录音，可共享语音队列与输出链路。第二个语音请求需要明确的忙碌处理；不能让两路帧混在同一解码器。

暂不直接缩小 BLE 堆、4 KiB 栈或音频池。应先测协议栈堆峰值、栈水位、重连/配对/长语音峰值，再定容量。

## 多连接仍需解决的事情

当前固件仍是一条连接、一个适配器、一份 peer 和一条语音流。即使省出 1 KiB，也不能据此确认支持两条 BLE 连接。后续还需要：

- 核对 SDK 多 central 连接配置与额外堆预算，实测连接调度。
- 为每连接独立保存 GATT 句柄、按键状态、认证、定时器、密钥和重连状态；发现工作区可以共享，运行状态不能混用。
- 扩展绑定持久化、设备管理以及 RBP/3 的设备枚举/来源路由；目前上位机来源字段只是为此准备，没有改变线协议的单设备语义。
- 定义单路语音仲裁，验证两遥控器同时按键、交错重连、拒绝第二语音请求和长录音。

建议下一步先做发现/运行状态拆分，保留单连接行为并回归；取得新 ELF 和实际内存水位后，再决定双连接预算。当前结论是**存在值得验证的 RAM 优化空间，多连接可行性尚未得到实测证明**。
